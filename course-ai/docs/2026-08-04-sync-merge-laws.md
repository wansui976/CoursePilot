# 同步合并律（收方向设计）

状态：待评审。本文只定合并语义，不含实现。
范围：七种同步记录各自的合并函数、收敛性论证、删除判定表、卡片×事件一致性契约、不同步清单。

---

## 0. 现状与两个结构性前提

出方向已完整：触发器入队、按（计数器, 设备）分配版本、删除留墓碑、出队有租约、
同一记录的未发送旧版会被新版顶掉（**合并式外发**——中间版本可能永远不被发出，
这一点约束了后文所有合并律的形态：只能依赖状态，不能依赖看到每一次变更）。

进方向为零。且现有结构里有两处必须先补上，否则任何 apply 都不可能正确：

**P1（版本向量）**：目前每条记录只存一个（计数器, 设备）对。两台设备各自改同一条
记录会得到 (5, A) 和 (9, B)——能看出"不同"，看不出 B 改之前有没有见过 A 的版本。
即：**现有版本号无法区分"更新"与"并发"**。凡是"并发时必须保留双方"的记录
（见笔记），需要把每条记录的版本从单对扩成按设备一行的小向量（实践中 ≤ 2–3 行），
信封携带写方的整个向量。比较规则：远端向量逐项 ≥ 本地 → 快进；≤ → 忽略；
不可比 → 并发，走该记录的冲突分支。不需要并发检测的记录（多数）不依赖 P1。

**P2（回声抑制的事务纪律）**：所有外发触发器都以"applying=0"为闸门，专为
apply 时抑制回声而设，但生产代码从未置位。义务：apply 循环必须在**同一个事务内**
置 1、写入、置回 0。开关若跨事务，进程在中途崩溃会让闸门永远关着——此后所有
本地修改都不再外发，且无任何报错。同事务则崩溃即整体回滚，不存在中间态。

另有三条较小的前提：
**P3**：事件去重依赖事件 id 的唯一索引（已存在，验收时确认）。
**P4**：全序含墙钟分量（见 §1），配对握手中已互报时间戳，应在握手时测钟差，
超过阈值（建议 5 分钟）拒绝同步并明示原因，而不是让 LWW 在歪钟上安静地选错。
**P5**：卡片契约要求"增量更新 ≡ 从事件重放"（见 §5 C4），这条等式需要一次性
的一致性验证，列入验收。

## 1. 总纲：每条合并律都必须是半格上的取并

**投递模型**：至少一次、乱序、可重复、丢失后重传直至确认；外发合并；无跨记录事务。

在这个模型下，唯一能免证收敛的办法是让每类记录的状态空间构成**交换半格**：
合并函数 ⊔ 满足交换、结合、幂等（ACI）。于是任何一台设备的最终状态
= 它收到过的所有版本的 ⊔，与到达顺序无关（交换+结合）、与重复次数无关（幂等）、
与丢失无关（重传后集合相同）。两台设备只要最终收到同一集合，状态必然相同；
出方向的租约+重试保证集合最终相同。**收敛性论证到此一次给出，
§3 逐类只需验证"该类的 ⊔ 是 ACI 的"。**

**全序**：凡选 LWW 的地方，比较键一律为（墙钟毫秒, 写方设备 id）的字典序。
这是全序，max 天然 ACI。钟差由 P4 约束；残余风险窗口 = 钟差本身，逐类注明后果。

**字段分层**：合并的单位不是整条记录，而是**字段组**。同一条记录里，
用户意图字段、度量字段、删除状态字段各走各的律，互不覆盖。这是判定表 §4
能同时做到"编辑不丢、删除不复活"的根基。

## 2. 七种记录的合并函数

输入统一为：本地状态 L、远端信封 R（含 payload 与版本信息）、双方版本。
输出为新本地状态。凡"忽略"均指不改本地、照常确认，不算失败。

### 2.1 课程

| 字段组 | 律 |
|---|---|
| name、updated_at | LWW（全序） |
| created_at | 首见即定（取双方较小值，min 是 ACI 的） |
| deleted_at | 独立 LWW，见 §4 |

改名冲突的败方直接丢弃：损失是一个名字，代价与冲突概率都低到不值得保留双方。
根目录路径本来就不外发（每台设备的文件系统各不相同），维持不发。

### 2.2 视频

三个字段组，三条律：

| 字段组 | 字段 | 律 |
|---|---|---|
| 意图 | title、course_id、order_index | LWW |
| 度量 | duration_ms、content_fingerprint | **有知胜无知**：一方为空另一方有值 → 取有值方；双方都有且相等 → 不变；双方都有且不等 → 见下 |
| 删除 | deleted_at | 独立 LWW，见 §4 |

**为什么度量不能 LWW**：没有媒体文件的设备，其记录里 duration 为空。它改个标题，
整条记录 LWW 会把"空时长"一并盖过去——这正是"空覆盖满"在已同步字段里的化身。
有知胜无知是平坦格（⊥ < 有值）上的取并，ACI 成立。

**指纹不等**：意味着两台设备在同一条记录名下放着**不同的文件**。此时度量字段
保持本地值（各自描述各自的文件），并把指纹分歧记入冲突表供界面提示。
"保持本地"单独看不满足交换律，但分歧本身已入冲突表、且不回写不外发，
对同步收敛无影响（同步层面双方状态各自稳定，分歧以显式记录收敛）。

**媒体不在本机的语义**（约束 5）：同步来的视频记录若本机无媒体文件，
记录是**完全体，只缺播放**。改名、笔记、卡片、进度一切可用；播放位显示
"此设备上没有媒体文件"，给两个出口：手动定位文件、或重新导入。导入时若新文件的
内容指纹与记录一致，**挂接到既有记录**而不是新建——这正是指纹进入同步载荷的用途。
占位记录进回收站走普通删除流程。

### 2.3 笔记

一视频一条，正文是用户手写或 AI 生成的富文本。**这是唯一一类"静默丢失不可接受、
且双方都可能是大段人写内容"的记录**，因此是唯一必须依赖 P1 并发检测的记录。

分层 LWW + 并发保全：

1. **层级**：有 user_edited_at 的版本（人改过）恒高于只有 ai_generated_at 的版本
   （纯机器产物）。层级不同 → 人写的一方胜，**无论墙钟先后**。
   理由：一台设备的流水线自动重生成笔记是机器行为，不得覆盖另一台上人的编辑。
2. **同层**：按向量比较。可比 → 取新；**并发 → 全序定可见的胜者，
   败方全文存入冲突表并在界面上可见可取回**。绝不静默丢。
3. 幂等与交换：层级 max、向量取并、全序 max 均 ACI；冲突表按
  （记录, 双方版本）定键，同一冲突重复投递只落一条。

不做正文级三方合并（富文本 CRDT）。冲突频率不配那台机器；保全 + 人工取回够用。

### 2.4 片段

起止区间 + 短备注，编辑罕见。整记录 LWW；检测到并发（若 P1 就位）时，
败方以**确定性副本**保留——副本 id 由（原 id, 败方版本）哈希导出，双方各自执行
会生成同一个副本 id，幂等不重复。两条片段并存无任何害处，用户手删其一即可。
删除状态照 §4。

### 2.5 学习事件

追加只增日志，库里已有触发器强制不可改不可删，事件 id 有唯一索引。

**律：按事件 id 取集合并**（G-Set）。已有则忽略，没有则插入。并集是 ACI 的教科书例。

推论：**开着同步就永远不准删除事件**——墓碑化任何一条事件都会破坏 §5 的折叠。
现状本就不删，把它从"现状"升格为"约束"。日志体积问题（若干年后）留给未决 §7。

### 2.6 记忆卡

库里已是两张表：**卡片身份**（属谁、正反面、出处）与**排期状态**
（稳定度/难度/到期/次数）。信封目前只装身份——这个划分正确，升格为契约（§5 C2）。

| 部分 | 律 |
|---|---|
| 身份内容字段 | LWW（正反面被两边同时改的概率可忽略；卡片多为机器生成，人只改错字） |
| 删除 | §4 |
| **排期状态** | **没有合并律。它不参与合并**——它是本地由事件折叠出的物化视图，见 §5 |

约束 2 的正面回答：两台各复习一次同一张卡，两条复习事件按 2.5 并集，双方各自
重新折叠，得到**包含两次复习的同一排期**。不取任何一方，也就不丢任何一方。

### 2.7 观看进度

| 字段 | 律 | 理由 |
|---|---|---|
| position_ms（续播点） | LWW（按 updated_at + 设备） | 续播点是"我最后看到哪"，不是单调量：用户故意回退开头重看，取 max 会把他弹回后面。语义上就该后者胜 |
| duration_ms | 有知胜无知（同 2.2） | 度量字段 |
| 累计观看时长、统计、热力图 | **不在本记录内合并**。它们全部由观看事件推导，事件按 2.5 并集后本地重算 | 两台各看 30 分钟，成对取 max 少算一台，成对相加则每次重放多算一次。唯一在重复投递下正确的累计 = 对事件集合求和，幂等由集合去重保证 |

## 3. 收敛性核对表

| 记录 | 合并形态 | ACI 依据 |
|---|---|---|
| 课程 | 字段组 LWW + min + 删除字段 LWW | 全序 max / min 均为半格取并 |
| 视频 | LWW + 平坦格取并 + 冲突表 | 同上；平坦格 ⊥<有值 |
| 笔记 | 层级 max ∘ 向量并 ∘ 全序 max，败方入冲突表 | 三层均取并；冲突键确定 → 幂等 |
| 片段 | LWW + 确定性副本 | 副本 id 为纯函数 → 双方产物相同、重复不增殖 |
| 事件 | 集合并 | G-Set |
| 卡片 | 身份 LWW；排期 = 视图 | 视图是集合并结果的确定函数：底收敛 ⇒ 视图处处相等 |
| 进度 | LWW + 平坦格；累计走事件 | 同上 |

跨类型问题两条：

**外键顺序**：子记录可能先于父记录到达（卡片先于视频、视频先于课程），
而到达顺序按约束不可假设。规则：**驻留重试**——外键不满足的信封搁置，
每个批次结束后重试全部搁置件；父记录到齐即消化。搁置不确认，出方重传兜底。
集合语义不受影响（最终应用的集合相同），只是有限延迟。

**折叠重算的事务边界**：见 §5 C4。

浮点确定性：折叠含浮点递推。两端为同一份代码、IEEE 754 语义、不开快速数学，
同输入同输出成立；列入验收而非假设。

## 4. 删除判定表

删除有三态：软删（回收站，可恢复）、过期清除 / 手动清空（不可逆）、
以及并发的编辑。核心手段是 §1 的字段分层——**deleted_at 是独立字段，
有自己的 LWW，内容编辑不碰它**。

| 情形 | 判定 | 为什么不违约 |
|---|---|---|
| A 软删，B 并发编辑内容 | 删除字段与内容字段各自合并 → **带着新内容躺进回收站** | 编辑一个字节都没丢（在回收站里）；删除意图也没被顺手撤销。双向都无损，且无需判定"谁的意图更真" |
| A 软删，B 恢复 | 同一字段的两次写 → LWW，晚者胜 | 双方都是对同一开关的显式操作，后表达的意图胜，确定且对称 |
| A 过期清除 / 清空回收站（硬删） | 硬删信封是**对回收站状态的确认，不是独立意图**：接收方本地仍在回收站（或已无此记录）→ 执行硬删、立墓碑；本地已恢复 → **忽略**。被忽略后，恢复方的保存照常外发，A 按下一行判定复活该记录 | 30 天保管期的价值恰恰在"每台设备都有反悔权"。若硬删无条件执行，一台设备的定时清理会跨设备杀掉另一台刚刚做出的恢复 |
| 墓碑已立，迟到的保存到达 | 保存的版本新于墓碑所记版本 → 复活（真实的恢复，对应上一行）；不新于 → 丢弃 | 后者的典型是离线 40 天的设备送来早已扔掉的旧编辑：内容已过保管期，用户在有效期内未反悔，按已过期处理。墓碑保留，防止同一具尸体反复诈尸 |
| 课程软删的级联 | 本地级联已逐条软删其视频并各自入队，远端逐条按上述规则并入，无需级联专规 | 可见性由"自身未删 且 课程未删"共同决定：视频若被另一台并发恢复，在课程恢复前仍呈现在回收站视图中，不产生孤儿 |
| 新建撞墓碑同 id | 不发生（id 为 UUID，不复用） | — |

"不让用户明确扔掉的东西复活"的总论证：能触发复活的只有两条路——
另一台设备上**晚于删除**的显式恢复，或**保管期内**的显式恢复顶掉过期清除。
两条都是用户本人更晚表达的意图；纯机器行为（AI 重生成、定时清理）在任何分支
都不具备复活或越权终结的能力。

## 5. 卡片 × 事件一致性契约

五条，合起来使"卡片状态与事件日志互相矛盾"**在构造上不可能**，
而不是靠小心维护。

- **C1（唯一事实源）** 复习历史的事实 = 复习事件（卡片 id、评分、时刻），
  不可变、按 §2.5 并集。排期表是它的**物化视图**，无独立事实地位。
- **C2（信封不载排期）** 卡片信封只含身份内容字段（现状已然，升格为契约）。
  接收方在任何情况下不从信封写排期。矛盾的来源被从线上拿掉了。
- **C3（折叠定义）** 排期(卡) = 以全序最新的**基线事件**为种子（无基线则从空卡起），
  将其后全部复习事件按（时刻, 事件 id）升序做 FSRS 递推。间隔天数由相邻事件
  时刻差给出。排序键含事件 id → 同毫秒事件也有确定顺序。
- **C4（重折叠义务）** 任一 apply 批次为卡 X 并入了新的复习或基线事件，
  必须**在同一事务内**重算 X 的排期视图。本地复习路径维持增量更新，
  合法性依据是"增量 ≡ 重放"（同一递推函数的两种执行形态），此等式列入验收（P5）。
  推论：晚到的**中间**事件会改写其后每一步折叠——这不是异常，是真实交错的正确结果；
  外在表现只是同步后到期日可能移动。
- **C5（不变式）** 任意设备任意时刻：排期(X) = 折叠(本地事件集, X)。
  本地复习必须**先落事件、同事务更新视图**，事件先行。

**基线事件**：一次性的迁移垫层，解决"事件重放无法复现的历史"——早于事件日志的
复习、以及排程算法从 SM-2 换代到 FSRS 时期的旧状态（当时的存量卡带着保留的到期日
但清零的稳定度，纯重放对不上）。首次开启同步时，对每张"当前排期 ≠ 本地折叠"的卡，
落一条不可变基线事件，内容为该卡此刻的完整排期状态。基线随事件一同同步；
折叠从最新基线起步。两台各自带历史开启同步 → 两条基线 → 全序选晚者为种子，
更早一方基线之前的零散事件被种子遮蔽——一次性的切换成本，量化且有界。

## 6. 不应同步的清单

| 东西 | 理由 |
|---|---|
| API 密钥、B 站 cookies、模型配置 | 机密 + 每台设备各有各的供应商与档位。密钥跨设备走人，不走库 |
| 媒体文件 | 体积；且"哪台机器有哪个文件"本来就是每台自己的事实（§2.2 占位语义） |
| 文稿、课件图片、AI 章节/摘要/笔记/习题/脑图 | 可再生的派生物。**不合并 ⇒ "空覆盖满"从根上不可能**。它们贵（真金白银 + 几十分钟），所以值得的是**显式搬运**（"从另一台设备取来"的手动动作，未来项），而不是后台合并——搬运有方向、有确认，合并两者皆无 |
| 概念及其排期 | 由 AI 提取 + 复习事件推导的二阶派生物。事件同步后本地可重建。若未来升为一等公民，照 §2.6 的"身份同步、排期折叠"同构扩展 |
| 排期表本身 | §5 C2 |
| 处理任务状态、用量统计、RAG 索引、Whisper 模型 | 设备本地的机器状态 |
| 界面偏好（面板宽度、停靠边…） | 跟着手走的东西不该跟着账号走 |
| 同步机制自身的表 | 元数据同步自身 = 递归灾难 |

## 7. 未决（实现前需拍板，不阻塞本文评审）

1. 冲突表的界面出口：笔记败方全文的呈现与取回交互。
2. 事件日志的长期体积（多年后数万条）：压实需要能改写历史的新机制，与 C1 冲突，
   届时需专门设计（例如带基线快照的分段封存），非今日问题。
3. 保管期常数（现 30 天）是否随同步进入用户可见的设置。
4. P4 的钟差阈值与提示文案。
5. 驻留重试的搁置上限与超时告警（防父记录永不到达时静默积压）。

## 8. 验收清单（对照原始约束）
