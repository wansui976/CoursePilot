# 应试类网课的低成本 Prompt 设计

日期：2026-07-29

针对本项目的实际内容形态（应试类网课：讲题型、讲审题、讲答题模板、带例题精讲），
重新设计笔记 / 出题 / 脑图 / 提问四类 Prompt，并回答一个前置问题：
**要不要把整份原始字幕直接丢给模型。**

---

## 0. 前置结论：不要丢原始字幕，但也别为省钱毁掉缓存

### 现状的三笔账

一节 90 分钟的中文网课，量级大致是：

| 成分 | 字符数 | 占比 | 说明 |
|---|---|---|---|
| 讲稿正文 | ~20,000 | ~65% | 按 220 字/分钟估 |
| 时间戳前缀 | ~8,000 | ~26% | ASR 约每 5 秒一段 → 约 1,000 段 × `[mm:ss] ` |
| 板书 OCR 行 | ~2,000 | ~7% | 已去重（`new_slide_lines`） |

**四分之一的输入是时间戳前缀**，而这几类任务根本不需要 5 秒粒度的时间锚点——
笔记和脑图只需要能标到「这个要点在第几分钟」，出题只需要 `ref_ms` 落在正确的段落里。

现在的做法是：五个产物（章节/摘要/笔记/出题/脑图）各发一次完整上下文，
上下文逐字节相同，所以除第一次外命中前缀缓存。这一点是**现有设计里最省的部分，
必须保住**——任何「给每个任务定制上下文」的方案都会让四次缓存命中全部作废，
省下的输入量远抵不过丢掉的缓存折扣。

同时还有一个真实缺陷（外部审计已指出，尚未修）：**五类产物都没有输入预算**。
三小时的长讲座正文可达 6 万字符以上，五个任务会依次撞上下文上限，连环失败。

### 结论

1. **不丢原始字幕，丢「规范化讲稿」**——在生成之前做一次无损压缩，五个任务共用同一份。
2. **压缩只做一次、结果唯一**，保证五个任务的上下文逐字节相同，前缀缓存照旧命中。
3. **加输入预算**：超过阈值先做一轮廉价的分块提要，再让五个任务基于提要稿工作。
4. **提问（QA）不走这条路**——那是检索问题，见第 4 节。

### 规范化讲稿（canonical context）

在 `lecture_context` 之后、送进 Prompt 之前加一层，只做这四件事：

1. **按时间窗合并分段**：把 ASR 的 5 秒碎段合并成约 45 秒一块，一块一个时间戳。
   时间戳开销从 ~8,000 字符降到 ~1,200，且不损失任何可用于定位的精度
   （产物里的 `[mm:ss]` 本来就是给人点击跳转用的，45 秒足够）。
2. **去口语填充词**：若字幕纠错已开启，这一步已经做过，不重复做。
3. **板书行保持现状**：已去重，且带 `(板书)` 标记（可信度不同，模型需要能区分）。
4. **超预算时降采样**：见下。

预期压缩比：**30k → 约 18k 字符（约 -40%）**，且对这四类任务零信息损失。

### 输入预算（两档）

| 规范化后长度 | 策略 |
|---|---|
| ≤ 20,000 字符 | 直接全文。简单、质量最好、缓存命中。绝大多数单节课落在这一档。 |
| > 20,000 字符 | 先做一轮 **map 提要**：按 12,000 字符切块，每块压成「≤300 字要点 + 3 条代表性原句（带时间戳）」，拼成「提要稿」；五个产物基于提要稿生成。 |

提要稿本身也要缓存复用：它是这个视频的第二份 canonical context，五个任务共用。
map 阶段用便宜的模型（路由里单独给一个 profile），reduce 阶段用主模型。

## 1. 低成本笔记 Prompt

### 现在的问题

现有笔记 Prompt 有 **17 行硬性结构要求**（题型定位/审题方法/方法论/作答技巧/
易错警示/答案示范/知识小结表格…），`max_tokens: 6144`。两个后果：

- **输出贵**：6144 输出 token 是所有任务里最贵的一项，而输出 token 通常比输入贵 3-5 倍。
- **结构强行凑满**：字幕里没讲「易错警示」时，模型倾向编一个，因为 Prompt 要求了。
  提示词里已经写了「没有的信息不要硬编」，但强结构与该约束是互相拉扯的。

### 设计

**核心思路：结构由内容决定，不由模板决定；把「小节齐全」换成「有依据才写」。**

```
system:
你是应试类网课的笔记助手。输出 Markdown，不要代码围栏。
写给「课后复习 + 考前速查」的人看：他没时间重看视频，要能直接用。

规则：
1. 只写视频真讲过的。任何一条都要能在讲稿里找到出处，找不到就不写。
   宁可整节缺失，也不要用常识补一个看起来合理的说法。
2. 每条要点末尾附 [mm:ss]，取自讲稿里该内容所在行的时间。不要编造时间。
3. 用「## 主题」分节，节内用 `- ` 列要点。要点写成可执行的动作或可判断的结论，
   不要写成「介绍了 X」这类目录式空话。
4. 老师给的口诀、模板、固定表述、判分点，**逐字保留**，不要改写成同义句——
   这些是拿分的东西，换个说法就废了。
5. 例题只在老师完整讲了解法时才写，格式固定为三行：
   题目 → 关键判断（他是怎么看出该用这个方法的）→ 答法。不要抄整道题面。
6. 结尾写一节「## 速查表」，Markdown 表格，列为：考点 | 怎么判 | 怎么答。
   只收本视频真正讲到的考点，三到八行。

user:
根据讲稿写笔记。
```

### 省在哪

- `max_tokens` 从 6144 降到 **3072**。上面的结构比原来紧凑，3000 token 足够一节课。
- 删掉「题型定位/审题方法/方法论/作答技巧/答案示范」五个固定小节，改为按内容分节：
  **系统提示本身缩短约 60%**（它每次调用都是全价，不在缓存前缀里）。
- 规则 4、5 是**质量**约束不是成本约束，但它们防住了这类笔记最常见的失败：
  把老师的原话改写成通顺但不能拿分的书面语。

## 2. 低成本出题 Prompt

### 现在的问题

`max_tokens: 4096`，要求 5-8 题、每题带解析。解析往往比题干长两三倍，
而复习时真正被读的是「答错之后看一眼为什么」——解析可以短。

另外现在**出题和笔记各自通读一遍全文**，这是重复劳动：出题需要的「考点清单」
和笔记的「速查表」是同一批信息。

### 设计

**核心思路：出题基于已生成的笔记速查表 + 讲稿，而不是从零通读。**

调用顺序改为：章节 → 笔记 → （出题、脑图并行，二者都能读到笔记）。
出题的上下文 = 规范化讲稿（缓存命中）+ 笔记速查表（约 500 字符，全价但很短）。

```
system:
你是应试类网课的出题助手。只输出 JSON 数组，不要解释或代码围栏。

user:
按下面的速查表出题，每个考点最多一题，总共 5-8 题。
输出 JSON 数组，每项：
{"type":"single"|"multi"|"judge","stem":题干,"options":[...],
 "answer":单选为字符串/多选为字符串数组/判断为 true|false,
 "explanation":一句话说明依据,"ref_ms":该考点在讲稿里的毫秒时间}

要求：
1. 考「会不会用」，不考「记不记得住」：题干给一个具体情境，问该怎么判断或怎么处理。
2. 干扰项必须是**老师明确讲过的易混点**；讲稿里没提到的混淆点不要造。
   造不出合格干扰项的考点，改出判断题，或者跳过。
3. single 至少 4 个选项；multi 至少 2 个正确项；judge 不给 options。
4. answer 用选项原文，不要用字母。
5. explanation 一句话，指出依据在讲稿哪个说法上；不要复述题干，不要展开教学。
6. ref_ms 取自讲稿真实时间，不要编造。
```

### 省在哪

- `max_tokens` 4096 → **2048**。解析从「说明为什么对、错在哪、并指出依据」
  收紧成一句话，这是输出侧最大的一笔。
- 规则 2 把「凑够 5-8 题」的压力泄掉了：造不出好干扰项就降级或跳过，
  避免模型为了凑数生成一眼能排除的垃圾选项——那种题既费 token 又没有复习价值。
- 复用笔记速查表，出题不必再自己从全文里归纳考点。

## 3. Mermaid 脑图 Prompt

### 前提：这会换掉渲染器

当前脑图渲染用的是 **markmap**（`markmap-lib` / `markmap-view`），输入是 Markdown 大纲。
改用 Mermaid 需要前端换成 Mermaid 渲染（`mermaid` 包，`mindmap` 图类型），
并且历史脑图（存的是 markmap Markdown）要么保留旧渲染器兼容，要么重新生成。

**建议：先不换。** Markmap 对「大纲 → 可折叠脑图」这件事更合适：
它天然支持折叠、缩放、大节点数，而 Mermaid 的 mindmap 在节点多时布局会拥挤，
且对中文长文本换行支持一般。真要换，理由应该是「想统一到 Mermaid 生态、
顺便支持流程图/时序图」，而不是脑图本身的效果。

下面给出 Mermaid 版本，供你决定后直接用。

```
system:
你是脑图助手。只输出一个 Mermaid mindmap 代码块的**内容**，
即以 `mindmap` 开头的若干行，不要代码围栏、不要任何解释。

user:
把这节课的知识结构整理成 Mermaid 脑图。要求：
1. 第一行是 `mindmap`，第二行是根节点 `  root((主题))`，主题不超过 10 字。
2. 用缩进表示层级，整体 3 层，最多 4 层。每层缩进两个空格。
3. 节点文字用精炼短语，不超过 14 字，不要整句、不要标点结尾。
4. 节点文字若含 `(` `)` `[` `]` `{` `}` 等字符，一律去掉——它们是 Mermaid 的语法字符。
5. 二级节点对应各章节/大模块，三级节点是该模块下真正讲到的知识点。
6. 只放讲稿真讲过的内容；宁可少一个分支，不要为了对称补一个。
```

### 两个必须写进 Prompt 的细节

- **规则 4（括号）**：Mermaid 的 mindmap 用 `((...))`、`[...]`、`{{...}}` 表示节点形状，
  中文内容里出现括号会直接把图打坏。这是 Mermaid 相对 markmap 最容易踩的坑。
- **规则 2（缩进）**：Mermaid mindmap 完全靠缩进定层级，模型输出缩进不稳时图会错乱。
  实现时应在渲染前做一次缩进规整（把 1/3 空格对齐到 2 的倍数），不要指望 Prompt 保证。

`max_tokens` 建议 **1536**（脑图是四类里最短的产物）。

## 4. 提问检索式 Prompt

### 结论：提问绝对不该丢整份字幕

前三类是「把整节课变成一份产物」，天然需要看全片。
提问是「找到相关的那几段并回答」——把全文丢进去等于每问一次就付一次全片的钱，
而且长视频还会触发 map-reduce，一次提问变成 N 次调用。

本项目已有的检索基础设施是**关键词检索**（中文二字组切词 + 课件 OCR 文本），
不是向量检索——`embeddings` 表、`Provider::embed`、`chunk_transcript` 都还在，
但**没有任何调用方**（见第 7 节）。提问应该走两段式：
**先检索出候选窗口，只把窗口喂给模型。**

### 检索层（不花 token）

1. 用 `query_terms` 切词，在讲稿分段和课件 OCR 文本里打分（已有 `hit_count`）。
2. 命中段落向前后各扩 30 秒形成**窗口**，重叠窗口合并。
3. 取分数最高的 6-10 个窗口，总量控制在 **4,000 字符以内**。
4. 命中数为 0 时不要退化成全文，走「没讲到」分支（见下）。

### Prompt

```
system:
你是这节课的答疑助手。只根据给到的片段回答。

user:
问题：{query}

下面是从这节课讲稿里检索出的相关片段（每段以 [mm:ss] 开头，段与段之间不连续）：
{windows}

要求：
1. 只用片段里的信息回答。片段之间是**不连续**的，不要假设它们前后相接，
   不要把两段拼成一个因果关系。
2. 每条结论后紧跟依据所在的 [mm:ss]，照抄片段里的时间，只用单个时间点。
3. 片段不足以回答时，直说「这节课讲到的部分只够回答到这里」，
   再说明缺的是什么。不要用你自己的知识补齐后混在一起讲。
4. 先给结论，再展开；不要复述问题，不要寒暄。
```

### 「没检索到」分支

检索命中为 0 时不要调模型去猜，直接告诉用户「这节课没讲到」，
并提供两个按钮：**在整门课里搜** / **让 AI 用自身知识回答（会标注来源）**。
这样零命中的提问花零 token，而用户仍有出路。

### 省在哪

- 单次提问输入从 ~30,000 字符降到 ~4,000，**约 -87%**。
- 长视频不再触发 map-reduce，一次提问就是一次调用（原来可能是 3-5 次）。
- 零命中的提问不调模型。

## 5. 汇总：改动清单与预期

| 项 | 现在 | 改后 |
|---|---|---|
| 讲稿规范化 | 无 | 合并 45 秒块、去填充词，约 -40% 字符 |
| 输入预算 | **无（长视频会失败）** | 两档，超阈值先 map 提要 |
| 笔记 max_tokens | 6144 | 3072 |
| 出题 max_tokens | 4096 | 2048 |
| 脑图 max_tokens | 4096 | 1536 |
| 出题输入 | 全文重新通读 | 讲稿（缓存）+ 笔记速查表 |
| 提问输入 | 全文（或 map-reduce） | 检索窗口 ≤4,000 字符 |
| 前缀缓存 | 五任务共用，已命中 | **保持不变**（这是硬约束） |

粗算：单节课的自动产出（章节+摘要+笔记+出题+脑图）输入侧约 -40%、输出侧约 -45%；
提问的单次成本约 -85%。真实数字取决于服务商的缓存折扣，需要接真 Key 实测。

## 6. 落地顺序建议

1. **先加输入预算**——这是在修一个真实缺陷（长视频五个任务连环失败），不只是省钱。
2. 再做讲稿规范化（合并时间块）。这一步单独就能省 25%，且不影响任何产物质量。
3. 再改提问的检索式 Prompt。省得最多，风险最低（不影响已生成的产物）。
4. 最后调四个 Prompt 与 `max_tokens`。这一步会改变产物风格，建议先在一两节课上对比。
5. Mermaid 脑图单独评估，不建议和上面几项捆绑。

## 7. 现有 RAG 的实际形态（写这份设计时查清的）

「RAG」在本项目里其实是**三条不同的路径**，只有一条真的在做检索。

### 7.1 单视频问答 —— 不检索，整篇喂

`rag::answer_stream`：把整份讲稿当上下文。

- 讲稿 ≤ 24,000 字符 → 一次调用，流式输出。
- 超过 → map-reduce：按 16,000 字符切块，逐块问同一个问题（非流式），
  块内无关时要求模型只回 `NONE` 并被丢弃；把非 NONE 的块答案拼起来再做一次综合（流式）。
- **不产出引用**（`citations: Vec::new()`）——因为没有"命中片段"这个概念，
  模型直接在正文里写 `[mm:ss]`。

这条路径是本次要改的重点：它是全项目最贵的一次调用，且长视频会退化成 3-5 次调用。

### 7.2 课程级问答 —— 真正的检索，但是关键词的

`rag::course_answer_stream` + `assemble_scope_context`，两段式：

1. **逐视频粗筛**：`scored_segments` 给每个字幕段打分，分数 = 该段命中了几个**不同**的
   查询词元（词元来自 `query_terms`，中文按二字组切）。每个视频只取前 8 段
   （`PER_VIDEO_TOPK`）。这一步的意义是**保证跨视频覆盖**——不这么切，
   一个高度相关的视频会把其余视频全挤出去。
2. **全局重排**：合并后按分数降序、时间升序，取前 40 段（`COURSE_CONTEXT_LIMIT`）。
3. 装配成 `〈视频标题 mm:ss〉文本` 的上下文，先发 `Citations` 事件让前端渲染可点的
   跨视频出处，再单次流式作答。
4. 零命中 → 不检索兜底，直接让模型用自身知识回答并强制标注「非课程内容」。

**第 4 节要给单视频问答做的，本质就是把这套搬过来**，再加上「命中段前后扩窗」。

### 7.3 文稿搜索 —— 纯本地，不花 token

`keyword_search` / `keyword_search_scope`：同一套词元打分，但同时搜**字幕段**和
**课件页 OCR 文本**，合并后排序（分数降序 → 课件页优先 → 时间升序），
课件命中还会带页图路径和页号给前端显示缩略图。

### 7.4 向量检索层是死代码

`migrations/0004_embeddings.sql` 建了 `embeddings` 表（含 `vector_json`），
`Provider::embed`（OpenAI 兼容 `/embeddings`）和 `chunk_transcript`（带重叠的分块）
都实现了，README 里也写着"RAG 完整实现"。

但现在：

- `embeddings` 表**没有任何写入方，也没有任何读取方**；
- `Provider::embed` **没有调用方**；
- `chunk_transcript` 只在自己的单测里被调用；
- `cmd_build_embeddings` **没有注册进 `invoke_handler`**，前端只在一个测试 mock 里
  还留着 `buildEmbeddings` 的名字。

也就是说向量路线建好之后被关键词路线取代了，但代码和表都没清掉。

**对本次设计的影响**：第 4 节的检索层不要指望"复用已有的向量检索"——那条路是断的。
按关键词做（成本为零、中文切词已经调好、课件 OCR 也在同一套里）完全够用；
真要上向量，那是另一个决定，要连带解决"嵌入模型的钱、重新索引的时机、
表结构（vector_json 存 JSON 数组做全表余弦）在几千段规模下的性能"三件事。

## 8. 各步的实现要点

### 第 1 步：输入预算（修缺陷）

- 位置：`pipeline/ai.rs` 的五个 `generate_*` 都以 `transcript_text(db, video_id)` 起手，
  预算逻辑加在这一处即可，五个任务自动受益。
- 新增 `budgeted_context(db, video_id) -> AppResult<String>`：
  长度 ≤ 阈值直接返回；超阈值走 map 提要。
- **提要要落库缓存**，否则五个任务各做一次 map，反而更贵。
  建议复用 `ai_artifact_sources` 的思路：新表或新 artifact 名存提要文本 + 讲稿指纹，
  指纹一致就直接取，字幕变了自动作废。
- map 阶段用便宜模型：给 `TaskRouting` 加一个 `digest` 任务（做法与刚加的
  `correction` 一样，`serde(default)` 兼容老配置）。
- 失败处理：map 某块失败时**不要**静默跳过（那会让产物少看一段却看不出来），
  按已有的「成品率门槛」思路处理——低于门槛就整体失败，让用户重试。

### 第 2 步：讲稿规范化

- 位置：`pipeline/ai.rs::lecture_context` 之后加一层 `normalize_context`，纯函数、易单测。
- 合并规则：相邻讲稿行累计到 ~45 秒或 ~200 字为一块，取块首时间戳；
  板书行**不合并**（它们本来就稀疏，且要保留 `(板书)` 标记）。
- **必须保证确定性**：同一份输入永远产出同一份输出，否则前缀缓存失效。
  不要在里面放任何时间/随机/HashMap 迭代顺序相关的东西。
- 单测要盯的：时间戳单调不减、合并后总字数不少于原文正文（只删空白和前缀）、
  板书行位置不变。

### 第 3 步：提问改检索式

- 复用 `query_terms` / `hit_count` / `scored_segments`。
- 新增"扩窗"：命中段前后各扩 30 秒 → 区间合并（区间重叠或相邻就并成一个）
  → 按总字符预算 4,000 截断（先按分数取，再按时间排序输出，保证读起来是顺序的）。
- 零命中不调模型：直接返回一个前端可识别的结果，由前端给"在整门课里搜 / 让 AI 用
  自身知识回答"两个按钮。
- 单视频问答从此**有引用了**（现在是空表），前端已有渲染引用的能力（课程级在用）。
- 回归风险：现在长视频走 map-reduce，改完之后不再有 map-reduce 路径。
  `map_reduce_answer_stream` 与 `map_reduce_answer` 可一并删掉，少一大块难测的代码。

### 第 4 步：调 Prompt 与 max_tokens

- 一次只改一类，改完在同一节课上对比新旧产物再动下一类。
- `max_tokens` 下调有个陷阱：JSON 类产物（章节/出题）**被截断就是解析失败**，
  不像 Markdown 少写一段还能用。出题降到 2048 之前，先确认 5-8 题 + 一句话解析
  的实际占用（可以在开发控制台看一次真实响应长度）。
- 笔记的结构改动会让**已有笔记与新笔记风格不一致**。刚做的「已过期」标记正好
  用得上：改完 Prompt 相当于换了口径，可以顺手把指纹算法带上 Prompt 版本号，
  让旧笔记自动标过期。

### 第 5 步：Mermaid（单独评估）

- 前端要引 `mermaid` 包并换掉 `MindmapPanel` 的 markmap 渲染。
- 历史脑图存的是 markmap Markdown，两种格式要能共存：
  建议在 `mindmaps` 表加一列 `format`（`markmap` / `mermaid`），按列选渲染器。
- 渲染前做缩进规整（1/3 空格对齐到 2 的倍数）与括号剥离，不要指望 Prompt 保证。
- 建议只有在"想统一到 Mermaid 生态、顺带支持流程图/时序图"时才做。
